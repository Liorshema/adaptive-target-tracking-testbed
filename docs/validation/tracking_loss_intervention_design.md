# Test-only intervention design

Production system preflight deliberately requires estimator/control topic agreement and derives predictor output from the control configuration. Editing owner topic parameters would either fail that contract or accidentally create competing oracle/ordinary publishers. Therefore the diagnostic wrapper invokes the unchanged production launch and applies scoped ROS remaps to the control node only. Ordinary estimator/predictor outputs remain intact. A test-only relay publishes exclusively on two diagnostic input topics; it never imports or publishes SafeVelocityCommand. The normal control node remains the sole command authority and the normal adapter owns actuation.

Robot oracle: on each ordinary estimator message, replace only [x,y,yaw,v,omega] with the latest nonfuture physical base sample, at most 0.08 s old, transformed world→odom using the actual spawn transform. Retain estimator joint position/velocity feedback, stamp, covariance and validation. This is an oracle for base localization, not joint estimation or full 6D base roll/pitch. Physical body twist follows the same Odometry child-frame contract; verify against finite differences offline. Covariance is retained for message compatibility, not claimed calibrated oracle uncertainty.

Target oracle: current/past physical target positions provide current position and backward finite-difference velocity. Publish a timestamped CV trajectory solely from that information, with the existing prediction dt/horizon. Use the existing launch lookahead override of zero, so the controller queries current state, with only short causal latency extrapolation. No future truth is read. This jointly removes the ordinary target-estimation/prediction/adaptation path and the 0.25 s lookahead; it does not isolate IMM from lookahead. Report this intervention explicitly, never as a perfect future-target oracle.

Four matched-initial-condition, seed-42, 90 s policies: baseline; robot oracle; current-target oracle; both. All share Scenario D physical dynamics/limits, controller task/weights, joint feedback and repaired motor backend. Reactive target paths may differ. Production code/config files must remain byte-identical. Require current inputs, complete physical safety, valid control coverage and owned cleanup; retain any failed attempt. Additional seeds only if necessary to separate alternatives.

Risks: causal base hold adds ≤0.08 s discretization; retaining estimated joints leaves joint error; backward target velocity has finite-difference lag; current-target oracle changes horizon policy; ROS scheduling may change initial target bootstrap. Compare only completed policies, disclose missing evidence, and use timestamp/frame/axis tests plus source/binary digests to establish diagnostic isolation.
